Introduction

Elliptic Curve Cryptography (ECC) is a fundamental building block of modern encryption. Unlike older systems like RSA that rely on the difficulty of factoring large numbers, ECC derives its security from the elliptic curve discrete logarithm problem — a mathematical puzzle that's computationally infeasible to solve even with powerful computers.

mobi-521 uses P-521, a specific elliptic curve standardized by NIST. This guide will walk you through the mathematical concepts step by step, building intuition for why elliptic curves provide such strong security with relatively small keys.

No Advanced Math Required

While we'll touch on some mathematical concepts, this guide is designed to be accessible. We'll build understanding gradually, using visual diagrams and analogies where possible.

What is an Elliptic Curve?

An elliptic curve is defined by a deceptively simple equation:

y² = x³ + ax + b

For P-521 (and most NIST curves), we use a = -3 and a specific value of b. When you plot this equation, you get a symmetric curve that looks roughly like this: 

         y
         |
         |        .-"""-.
         |     .'         `.
         |    /             \
    -----.---/--------------\------------ x
         |  /                \
         | /                  \
         |/                    \
         |
         |

But here's the crucial difference: we don't work with real numbers. Instead, we work with points on the curve over a finite field — essentially, arithmetic modulo a very large prime number.

The Prime for P-521

P-521 uses the Mersenne prime:

p = 2521 - 1

This is a number with 157 decimal digits. All arithmetic on the curve happens modulo this prime, which means we're working with integers from 0 to p-1.

Why Finite Fields?

Working over a finite field gives us two critical properties:

  • Discrete structure: There are only finitely many points on the curve (approximately 2521 for P-521)
  • Computational hardness: Certain operations become one-way functions — easy to compute forward, practically impossible to reverse

Point Addition

The magic of elliptic curves comes from defining an addition operation on points. Given two points P and Q on the curve, we can "add" them to get a third point R = P + Q.

Geometric Intuition (Over Real Numbers)

To add points P and Q:

  1. Draw a line through P and Q
  2. This line intersects the curve at a third point R'
  3. Reflect R' across the x-axis to get R = P + Q
         |
         |     P
         |      *
         |       \
         |        \    R'
         |         *---*------- line through P and Q
         |          \ /
         |           * Q
    -----|-----------------
         |          /
         |         * R (P+Q, reflected)
         |
Key Insight

This geometric operation has a purely algebraic formula that works in finite fields too. The coordinates of R can be computed directly from the coordinates of P and Q using modular arithmetic.

Special Cases

  • Point at infinity (𝒪): Acts as the identity element (like 0 for regular addition). P + 𝒪 = P
  • Point doubling: Adding a point to itself (P + P) uses the tangent line instead
  • Inverses: Every point P has an inverse -P such that P + (-P) = 𝒪

Scalar Multiplication

Scalar multiplication is repeated addition. Given a point P and an integer k, we compute:

Q = k · P = P + P + P + ... + P (k times)

For example:

  • 3·P = P + P + P
  • 5·P = P + P + P + P + P
  • 100·P = P added to itself 100 times

Efficient Computation: Double-and-Add

Naively adding P to itself k times would be slow. Instead, we use the double-and-add algorithm, which is similar to binary exponentiation: 

To compute 25·P:
  25 in binary = 11001

  Start with result = 𝒪
  Bit 1 (leftmost):  result = P
  Bit 1:             result = 2·result + P = 3·P
  Bit 0:             result = 2·result = 6·P
  Bit 0:             result = 2·result = 12·P
  Bit 1 (rightmost): result = 2·result + P = 25·P

This takes only O(log k) operations instead of O(k).

Forward is Fast

Computing Q = k·P is very efficient, even for astronomically large values of k (like 2256).

The Discrete Logarithm Problem

Here's where cryptographic security comes in. Scalar multiplication is a trapdoor function:

The Asymmetry

Easy direction (forward):

Given k and P, compute Q = k·P → Fast!

Hard direction (reverse):

Given Q and P, find k such that Q = k·P → Computationally infeasible!

This reverse problem is called the Elliptic Curve Discrete Logarithm Problem (ECDLP). No efficient classical algorithm exists to solve it. The best known algorithms take exponential time — for P-521, you'd need roughly 2260 operations, which is far beyond the reach of any computer.

Why It's Hard

Unlike regular multiplication (where you can use division to reverse it), or even modular exponentiation (where some special structure can be exploited), the elliptic curve operation provides no shortcuts. The curve's geometry, combined with the finite field arithmetic, creates a mathematical maze with no known exit.

Quantum Threat

Shor's algorithm (running on a large quantum computer) could solve ECDLP in polynomial time. However, such quantum computers don't currently exist. Post-quantum alternatives are being standardized for long-term security.

ECDH: Elliptic Curve Diffie-Hellman

ECDH is a key exchange protocol that lets two parties agree on a shared secret over an insecure channel, without ever transmitting the secret itself.

The Protocol

Alice                                       Bob
------                                     -----
Choose random secret: a                   Choose random secret: b
Compute public key: A = a·G               Compute public key: B = b·G

         Send A →
                    ← Send B

Compute shared: S = a·B                   Compute shared: S = b·A
              = a·(b·G)                                  = b·(a·G)
              = (a·b)·G                                  = (a·b)·G

Both parties now have S = (a·b)·G as the shared secret!

G is the generator point, a fixed point on the curve known to everyone. The crucial properties:

  • Alice's public key A = a·G can be shared publicly
  • Bob's public key B = b·G can be shared publicly
  • An eavesdropper sees A and B, but cannot compute a or b (ECDLP is hard!)
  • Without a or b, the eavesdropper cannot compute S = (a·b)·G
This is how mobi-521 encryption works!

When encrypting to a recipient's public key, mobi-521 generates an ephemeral key pair, performs ECDH, and derives the file encryption key from the shared secret using HKDF-SHA512.

Forward Secrecy

By using a fresh random value a for each encryption (ephemeral keys), mobi-521 ensures that even if your long-term private key is later compromised, past encrypted files remain secure (assuming the ephemeral private keys weren't stored).

ECDSA: Elliptic Curve Digital Signature Algorithm

ECDSA provides digital signatures — proof that a message came from the holder of a specific private key, and that the message hasn't been tampered with.

Key Generation

  • Choose random private key: d (a large integer)
  • Compute public key: Q = d·G

Signing (Creating a Signature)

To sign a message m with private key d:

  1. Hash the message: h = SHA512(domain_tag || m)
  2. Choose random nonce: k (must be unique for each signature!)
  3. Compute point: R = k·G = (x, y)
  4. Compute signature values:
    r = x mod n s = k-1(h + r·d) mod n
  5. The signature is the pair (r, s)
Nonce Security is Critical

If the same nonce k is used twice with the same private key, or if k can be predicted, the private key can be recovered! mobi-521 uses hedged signatures (RFC 6979 + randomness) to prevent this.

Verification (Checking a Signature)

Anyone with the public key Q can verify:

  1. Hash the message: h = SHA512(domain_tag || m)
  2. Compute:
    u₁ = h·s-1 mod n u₂ = r·s-1 mod n
  3. Compute point: R' = u₁·G + u₂·Q
  4. Check if R'.x mod n == r

If the check passes, the signature is valid! The mathematics ensures this only works if the signature was created by someone who knows the private key d.

Domain Separation in mobi-521

mobi-521 prepends b"mobi-521-sign-v1\x00" before hashing messages for signatures. This ensures that a signature created for encryption cannot be misinterpreted as a signature for a user message, preventing cross-protocol attacks.

Why P-521?

P-521 is one of the NIST P-curves, standardized in FIPS 186-4. Here's why mobi-521 chose it:

1. Mersenne Prime Structure

p = 2521 - 1

This special form (a Mersenne prime) allows for very efficient modular reduction. Arithmetic operations are faster than with generic primes of similar size.

2. Security Margin

P-521 provides approximately 260 bits of security. This is substantially higher than:

  • P-256: ~128 bits of security
  • X25519 (Curve25519): ~128 bits of security
  • Ed25519: ~128 bits of security

While 128-bit security is sufficient for most applications today, P-521's higher margin provides defense-in-depth against future cryptanalytic advances and increased computational power.

3. Long-term Data Protection

Data encrypted today may need to remain confidential for decades. P-521's 260-bit security provides a larger buffer against:

  • Moore's Law (exponential growth in computing power)
  • Algorithmic improvements in solving ECDLP
  • "Harvest now, decrypt later" attacks where adversaries store encrypted data to decrypt in the future

4. Well-Studied and Standardized

As a NIST standard, P-521 has been extensively analyzed by cryptographers worldwide. While some concerns exist about potential NSA influence on the random seed used to generate curve parameters, no practical weaknesses have been discovered.

Trade-offs

P-521 operations are slower than smaller curves like P-256 or X25519. However, for file encryption and signatures, this performance difference is negligible compared to symmetric encryption time. The security margin is worth the trade-off.

Comparing Elliptic Curves

Curve Security Level Key Size Used By Notes
P-256 ~128 bits 256 bits TLS, Bitcoin NIST standard, widely supported
P-384 ~192 bits 384 bits TLS, government Middle ground security level
P-521 ~260 bits 521 bits mobi-521 Highest NIST security, Mersenne prime
Curve25519 ~128 bits 255 bits age, Signal, SSH Designed for performance, twist-secure
Ed25519 ~128 bits 255 bits SSH keys, Git Signature-optimized variant of Curve25519
secp256k1 ~128 bits 256 bits Bitcoin, Ethereum Koblitz curve, efficient endomorphism

NIST P-curves vs Curve25519

Curve25519 Advantages:

  • Designed by Daniel J. Bernstein with security as the primary goal
  • Faster operations due to Montgomery form and field choice
  • Twist-secure (safe against certain implementation attacks)
  • No concerns about NIST/NSA influence on parameters
  • Simpler, harder to implement incorrectly

P-521 Advantages:

  • Significantly higher security margin (260 vs 128 bits)
  • Government/industry standard (FIPS 186-4)
  • Mersenne prime provides efficient arithmetic
  • Extensively studied for decades
  • Better for long-term data protection

Why mobi-521 Chose P-521 Over X25519

While age and rage use X25519 (the Diffie-Hellman variant of Curve25519), mobi-521 prioritizes maximum security margin for long-term data protection. The performance difference is negligible for file encryption, but the 260-bit vs 128-bit security difference is substantial for data that may need to remain confidential for decades.

Security Considerations

Random Number Generation

ECC security depends critically on high-quality randomness:

  • Private keys must be uniformly random across the entire key space
  • Ephemeral keys (ECDH) must be fresh and unpredictable for each session
  • Signature nonces (ECDSA) must never repeat or be predictable

mobi-521 uses the operating system's cryptographically secure RNG (via Rust's getrandom crate). ECDSA signatures use hedged nonces (RFC 6979 + randomness) to protect against RNG failures.

Side-Channel Attacks

Implementation matters! Naive implementations can leak secrets through:

  • Timing attacks: Different execution times for different private key bits
  • Power analysis: Measuring power consumption during operations
  • Cache attacks: Observing CPU cache access patterns

mobi-521 uses constant-time implementations from the RustCrypto ecosystem to mitigate timing attacks. However, full protection against sophisticated side-channel attacks requires careful operational security (secure hardware, physical isolation, etc.).

Quantum Computing

As mentioned earlier, Shor's algorithm can break ECDLP in polynomial time on a large quantum computer:

  • Classical security: P-521 requires ~2260 operations to break
  • Quantum security: Shor's algorithm reduces this to ~polynomial in 521

Current quantum computers are nowhere near this capability. However, if you're encrypting data that must remain secure for 20+ years, consider:

  • Monitoring NIST's post-quantum cryptography standardization
  • Planning migration to post-quantum algorithms when mature
  • Using hybrid encryption (classical + post-quantum) for critical data
Harvest Now, Decrypt Later

Adversaries with quantum computing ambitions may be storing encrypted data today to decrypt in the future. For ultra-sensitive long-term data, this threat model should be considered.

Implementation Vulnerabilities

Even with mathematically secure algorithms, implementation bugs can compromise security:

  • Buffer overflows in C implementations
  • Incorrect parameter validation
  • Weak random number generators
  • Reuse of ephemeral keys or nonces

mobi-521 is written in Rust, which provides memory safety guarantees and prevents many common implementation errors. The cryptographic primitives come from audited libraries (RustCrypto).
