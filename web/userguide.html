Overview

mobi-521 is a modern file encryption tool built on P-521 elliptic curve cryptography. It provides both a command-line interface and a browser-based web UI for encrypting files and messages.

Unlike age/rage (which uses X25519/Ed25519), mobi-521 is built entirely on the NIST P-521 curve (2521 - 1, a Mersenne prime), offering 256-bit security strength with higher safety margins for long-term data protection.

Not Compatible with age/rage

mobi-521 uses a different cryptographic stack and file format. Files encrypted with age cannot be decrypted with mobi-521, and vice versa.

Key Features

  • P-521 ECDH key exchange with ephemeral sender keys
  • HKDF-SHA512 key derivation
  • ChaCha20-Poly1305 symmetric encryption in STREAM mode (64 KiB chunks)
  • ECDSA-P521-SHA512 digital signatures with hedged nonces
  • Bech32m key encoding for error detection
  • QR code generation for keys (ASCII terminal + PNG export + printable PDF key cards)
  • Clipboard integration on all major platforms
  • WebAssembly support for browser-based encryption

Piping & Shell Integration

mobi-521 fully supports Unix pipes. When data is piped in, it automatically reads from stdin and writes to stdout (bypassing clipboard):

Basic Piping

# Encrypt piped data
echo "secret message" | mobi521 encrypt -r mobi521...

# Full encrypt → decrypt pipeline
echo "hello" | mobi521 encrypt -r mobi521... | mobi521 decrypt -i key.txt

Practical Examples

# Encrypt environment variables
echo "DATABASE_URL=postgres://..." | mobi521 encrypt -r mobi521... > db.m521

# Encrypt a git diff
git diff | mobi521 encrypt -r mobi521... > patch.m521

# Decrypt and apply patch
mobi521 decrypt -i key.txt patch.m521 | git apply

# Encrypt command output
ls -la /secret | mobi521 encrypt -r mobi521... > listing.m521

# Encrypt tarball on-the-fly
tar czf - ./secret-folder | mobi521 encrypt -r mobi521... > backup.m521

# Decrypt and extract
mobi521 decrypt -i key.txt backup.m521 | tar xzf -

Pipe Behavior

Input Output Behavior
Piped (stdin) No -o stdin → stdout
Piped (stdin) -o FILE stdin → File
Interactive (TTY) No -o Clipboard → Clipboard
File specified No -o File → stdout
Automatic Detection

mobi-521 automatically detects whether stdin is a pipe or an interactive terminal. No flags needed — just pipe data in and it works.

Key Generation

Generate a new P-521 key pair for encryption and signing.

Basic Usage

# Print both keys to stdout
mobi521 keygen

# Output:
# Public key: mobi521...
# MOBI521-SECRET-KEY-...

Save to File

# Write private key to file, print public key to stderr
mobi521 keygen -o identity.txt

# The identity file contains:
# - A comment with the public key
# - The private key on a single line

With QR Codes (ASCII)

# Display QR codes in terminal
mobi521 keygen --qr

# Shows:
# - Public key QR code (safe to share)
# - Private key QR code (keep secret!)
# - Warning about terminal history
Security Warning

When using --qr, QR codes containing your private key are displayed in the terminal. Clear your terminal scrollback buffer after use to prevent unauthorized access.

With QR PNG Export

# Save QR codes as PNG images (requires --features qr-png at build time)
mobi521 keygen --qr --qr-png mykey

# Creates:
# - mykey_public.png (200×200px, safe to share)
# - mykey_secret.png (200×200px, KEEP SECRET!)
Critical: Private Key QR Codes

QR codes of private keys contain your entire identity. Treat PNG files with private key QR codes with the same security as the private key itself. Do not share, upload to cloud services, or print without secure storage.

Export PDF from Existing Keys

Generate key card PDFs from existing identity files using the export-pdf command:

# From identity file
mobi521 export-pdf --identity identity.txt

# From raw key string
mobi521 export-pdf --identity "MOBI521-SECRET-KEY-..."

# Custom output filename
mobi521 export-pdf --identity identity.txt -o backup-card.pdf

# Single card (no duplicate)

The export-pdf command accepts the same identity formats as decrypt and sign:

  • Path to an identity file containing the private key
  • Raw private key string starting with MOBI521-SECRET-KEY-
When to use export-pdf

Use export-pdf when you already have a key pair and want to create a physical backup. Use keygen --card-pdf when generating a new key pair.

Key Format

  • Public keys start with mobi521 (lowercase)
  • Private keys start with MOBI521-SECRET-KEY- (uppercase)
  • Both use Bech32m encoding with built-in checksums
  • Keys are fixed-length and self-describing

Encryption

Encrypt files or messages using a recipient's public key.

Encrypt a File

mobi521 encrypt -r mobi521... plaintext.txt -o encrypted.m521

Encrypt from stdin

echo "secret message" | mobi521 encrypt -r mobi521... -o secret.m521

Encrypt from Clipboard

# Copy text to clipboard, then:
mobi521 encrypt -r mobi521...

# Encrypted output is now in clipboard

Using Default Recipient

Set a default recipient to avoid typing -r every time:

# Set up once
mkdir -p ~/.config/mobi521
echo "mobi521..." > ~/.config/mobi521/default-recipient

# Then encrypt without -r
mobi521 encrypt secret.txt -o secret.m521

Output Options

Option Behavior
-o FILE Write ciphertext to file
No -o, no input file Clipboard → Clipboard
No -o, file input File → stdout

File Extension

Encrypted files use the .m521 extension by convention. The file format is described in the File Format section.

Decryption

Decrypt files or messages using your private key.

Decrypt a File

mobi521 decrypt -i identity.txt encrypted.m521 -o plaintext.txt

Decrypt with Raw Key String

mobi521 decrypt -i "MOBI521-SECRET-KEY-..." encrypted.m521 -o plaintext.txt

Decrypt from Clipboard

# Copy encrypted text to clipboard, then:
mobi521 decrypt -i identity.txt

# Decrypted plaintext is now in clipboard

Decrypt to stdout

mobi521 decrypt -i identity.txt encrypted.m521

Identity File Format

Identity files contain a private key and optionally a comment with the public key:

# mobi-521 identity file
# public key: mobi521...
MOBI521-SECRET-KEY-...

The -i flag accepts either:

  • A path to an identity file
  • A raw private key string starting with MOBI521-SECRET-KEY-

Binary vs Text Output

mobi-521 automatically detects whether decrypted data is UTF-8 text or binary:

  • UTF-8 text: Displayed as-is in terminal or clipboard
  • Binary data: Displayed as hex dump (first 256 bytes) in terminal, full binary in clipboard

Always use -o to save binary files to preserve exact bytes.

Digital Signatures

Create and verify ECDSA-P521-SHA512 digital signatures.

Sign a Message

# Sign a file
mobi521 sign -i identity.txt document.pdf -o document.sig

# Sign from stdin
echo "hello world" | mobi521 sign -i identity.txt > signature.txt

Verify a Signature

# Verify a file signature
mobi521 verify -p mobi521... -s document.sig document.pdf

# Verify from stdin
echo "hello world" | mobi521 verify -p mobi521... -s signature.txt

Signature Format

Signatures are base64-encoded ECDSA signatures:

  • Algorithm: ECDSA-P521-SHA512
  • Nonce: Hedged (RFC 6979 + randomness)
  • Domain separation: b"mobi-521-sign-v1\x00" prepended before hashing
  • Output: Base64-encoded signature bytes
Breaking Change (v0.3.0+)

Signatures created before v0.3.0 are incompatible due to domain separation changes. All messages must be re-signed with the current version.

Same Keys for Encryption and Signing

mobi-521 uses the same P-521 key pair for both encryption and signing. This is secure due to:

  • Domain separation in signing (prevents cross-protocol attacks)
  • Different cryptographic operations (ECDH vs ECDSA)
  • Different key usage contexts

Verification Output

# Valid signature
$ mobi521 verify -p mobi521... -s doc.sig doc.pdf
✓ Signature is valid.

# Invalid signature
$ mobi521 verify -p mobi521... -s wrong.sig doc.pdf
✗ Signature is NOT valid.

File Format

mobi-521 uses a custom file format (version 3) inspired by age but not compatible with it.

Structure

m521.app/encrypted/v3\n
-> p521 <bech32m-ephemeral-pubkey>\n
<base64(encrypted-file-key)>\n
---\n
<binary STREAM payload>

Header

  • Magic string: m521.app/encrypted/v3
  • Recipient stanza: -> p521 <ephemeral_public_key>
  • Encrypted file key: Base64-encoded, derived via ECDH + HKDF
  • Separator: ---

Payload

The payload uses the ChaCha20-Poly1305 STREAM construction:

base_nonce (12 bytes)
|| ChaCha20-Poly1305(chunk_0)  # 64 KiB + 16-byte tag
|| ChaCha20-Poly1305(chunk_1)
|| ...
|| ChaCha20-Poly1305(final_chunk)  # ≤ 64 KiB + 16-byte tag

Nonce Derivation

Per-chunk nonce = base_nonce XOR (counter[8..12] || final_flag[7])

  • counter: 32-bit chunk counter (starts at 0)
  • final_flag: 0x01 for last chunk, 0x00 otherwise

STREAM Properties

  • Chunk size: 64 KiB (65,536 bytes)
  • Authentication: Each chunk has a 16-byte Poly1305 tag
  • Truncation protection: Truncated files always fail authentication due to missing final chunk flag
  • Streaming: Can decrypt chunk-by-chunk without loading entire file into memory
Why STREAM?

The STREAM construction ensures that partial or truncated ciphertexts cannot be decrypted. If an attacker removes the end of a file, the final chunk will not have the final flag set, and decryption will fail.

Key Derivation

File encryption key is derived via:

  1. Generate ephemeral P-521 key pair (sender)
  2. Perform ECDH with recipient's public key
  3. Derive shared secret via HKDF-SHA512:
    • IKM: ECDH output
    • Salt: None
    • Info: b"m521.app/encrypted/v3"
    • Output length: 32 bytes

Security Considerations

Cryptographic Primitives

mobi-521 uses well-established, peer-reviewed cryptographic algorithms:

  • P-521: NIST standard curve, 256-bit security strength
  • HKDF-SHA512: IETF RFC 5869 key derivation
  • ChaCha20-Poly1305: IETF RFC 8439 AEAD
  • ECDSA-P521-SHA512: FIPS 186-4 signatures with hedged nonces

Key Management Best Practices

  • Generate keys on a trusted, malware-free system
  • Store private keys encrypted at rest (use disk encryption)
  • Never share private keys via insecure channels (email, chat, etc.)
  • Use QR codes for air-gapped transfers, not network transmission
  • Keep multiple backups of private keys in secure locations
  • Consider hardware security modules (HSMs) for high-value keys

Forward Secrecy

mobi-521 provides forward secrecy through ephemeral ECDH:

  • Each encrypted file uses a unique ephemeral sender key
  • Compromising a recipient's private key does not decrypt past messages (if ephemeral keys are not stored)
  • However, the recipient's private key is reused, so compromise affects future decryption
No Built-in Key Rotation

mobi-521 does not enforce key rotation. For long-term security, periodically generate new key pairs and re-encrypt data.

Metadata Leakage

The file format reveals:

  • Approximate plaintext size (from ciphertext length)
  • Ephemeral public key (not sensitive, changes per encryption)
  • Protocol version

The format does NOT reveal:

  • Recipient's identity or public key
  • Plaintext content
  • Sender's identity

Side-Channel Attacks

mobi-521 relies on the Rust RustCrypto ecosystem for constant-time implementations:

  • ECDH and ECDSA use constant-time field arithmetic
  • ChaCha20-Poly1305 is inherently resistant to timing attacks
  • Key comparisons use constant-time equality checks

However, full side-channel resistance requires careful environment setup (no shared CPU caches, etc.).

Post-Quantum Resistance

P-521 is NOT quantum-resistant. A sufficiently powerful quantum computer running Shor's algorithm could break P-521 ECDH and ECDSA.

For post-quantum security:

  • Wait for NIST post-quantum standards to mature
  • Consider hybrid encryption (classical + post-quantum)
  • Re-encrypt sensitive data when post-quantum algorithms are standardized
Quantum Threat Timeline

Large-scale quantum computers capable of breaking P-521 do not currently exist. However, data encrypted today may be stored and decrypted in the future when quantum computers are available ("harvest now, decrypt later" attacks).

Signature Hedged Nonces

mobi-521 uses hedged ECDSA nonces (RFC 6979 + randomness) to protect against:

  • Weak RNG attacks
  • Nonce reuse (catastrophic for ECDSA)
  • Side-channel extraction of nonces

Defense in Depth: Layered Encryption

For high-security scenarios, mobi-521 works excellently inside other encrypted communication channels. This provides multiple independent layers of protection.

Example: mobi-521 + Signal/WhatsApp

Layered Security Approach

  1. Encrypt file with mobi-521 (P-521 ECDH + ChaCha20-Poly1305)
  2. Send .m521 file via Signal/WhatsApp (Signal Protocol E2EE)
  3. Recipient decrypts with mobi-521 (requires their private key)

Benefits of Layered Encryption

  • Multiple independent cryptographic systems: Breaking one layer doesn't compromise the other
  • Different threat models: Protects against compromise of either encryption system
  • Metadata separation: Messaging app sees who you're communicating with, but only encrypted blobs
  • Forward secrecy at both layers: Signal Protocol + mobi-521 ephemeral keys
  • Protection against backdoors: If messaging app is compromised or backdoored, content remains encrypted
  • Regulatory resilience: Some jurisdictions may compel messaging providers to weaken encryption

Use Cases for Layered Encryption

  • Journalists and sources: Protect sensitive documents even if Signal is compromised
  • Whistleblowers: Multiple layers reduce single points of failure
  • Legal professionals: Attorney-client privilege with technical guarantees
  • Healthcare: HIPAA-compliant data transfer with redundant protection
  • Activists in hostile environments: Protection against state-level adversaries
  • Financial data: Sensitive transactions requiring maximum confidentiality

Alternative Secure Channels

mobi-521 encrypted files (.m521) can be sent through any channel — you don't need to trust the transport:

  • Encrypted messaging: Signal, WhatsApp, Telegram (secret chats), Wire
  • Email: Even unencrypted email becomes a secure transport (content is already encrypted)
  • Cloud storage: Dropbox, Google Drive, OneDrive (zero-knowledge for provider)
  • File sharing: WeTransfer, send.vis.ee, OnionShare
  • Physical media: USB drives, SD cards (encrypted at rest)
  • QR codes: Small files can be transmitted via QR code scanning
Zero Trust in Transport

With mobi-521, you don't need to trust the transport layer. The .m521 file is safe to send through completely untrusted channels because the content is already end-to-end encrypted with your recipient's public key.

Practical Example

# Alice encrypts sensitive document
mobi521 encrypt -r bob_public_key document.pdf -o document.m521

# Alice sends document.m521 via Signal to Bob
# (Signal provides E2EE transport layer)

# Bob receives and decrypts with his private key
mobi521 decrypt -i bob_identity.txt document.m521 -o document.pdf

# Result: Two independent encryption layers
# - Signal Protocol protected the .m521 file in transit
# - mobi-521 protects the document content end-to-end

Comparison: Single vs Layered Encryption

Scenario Signal Only Signal + mobi-521
Signal Protocol compromised ❌ Content exposed ✅ Content still encrypted
Signal forced to add backdoor ❌ Backdoor can read content ✅ Backdoor only sees encrypted blobs
Device seizure (Signal DB extracted) ❌ Plaintext in local database ✅ Still need mobi-521 private key
Forward secrecy ✅ Signal Protocol provides it ✅✅ Both layers provide it
Metadata protection ⚠️ Signal sees who talks to whom ⚠️ Same (metadata same at transport layer)
When to Use Layered Encryption

Not every communication requires this level of security. Use layered encryption when:

  • Data must remain confidential for years or decades
  • You're operating in a high-threat environment
  • Regulatory or legal requirements demand maximum protection
  • Single point of failure is unacceptable
  • You want protection against future vulnerabilities in messaging protocols

Troubleshooting

Clipboard Not Working

Wayland

Symptom: clipboard unavailable, falling back to stdin/stdout

Solution: Install wl-clipboard:

# Debian/Ubuntu
sudo apt install wl-clipboard

# Arch
sudo pacman -S wl-clipboard

# Fedora
sudo dnf install wl-clipboard

# Nix
nix develop  # includes wl-clipboard

X11/macOS/Windows

Symptom: Clipboard operations fail or fall back to stdin/stdout

Solution: Ensure display server is running and accessible. On headless systems, clipboard will not work — use stdin/stdout instead.

QR PNG Not Available

Symptom: --qr-png flag not recognized or errors at runtime

Solution: Rebuild with default features enabled:

# PNG support is enabled by default
cargo build --release -p mobi521

# If you previously built with --no-default-features, remove that flag

WASM Not Loading in Web UI

Symptom: "Could not load WASM" error in browser

Solution: Rebuild WebAssembly module:

wasm-pack build crates/wasm --target web --out-dir ../../web/pkg

Then hard-refresh the browser (Ctrl+Shift+R or Cmd+Shift+R).

Decryption Fails

Wrong Private Key

Error: decryption failed

Cause: Using a different private key than the one corresponding to the recipient public key

Solution: Ensure you're using the correct identity file

Corrupted Ciphertext

Error: authentication tag verification failed

Cause: File was modified or truncated

Solution: Obtain an uncorrupted copy of the ciphertext

Version Mismatch

Error: unsupported format version

Cause: Attempting to decrypt a file encrypted with an incompatible version

Solution: Use the same version of mobi-521 that created the ciphertext, or re-encrypt with current version

Signature Verification Fails

Symptom: Valid signatures show as invalid

Common causes:

  • Wrong public key (not matching the signer's key)
  • Message was modified after signing
  • Signature created with old version (pre-v0.3.0 without domain separation)
  • Incorrect signature file or base64 decoding issue

Performance Issues

Large Files

mobi-521 uses streaming encryption and should handle large files efficiently. If you experience slowness:

  • Ensure you're using release builds (--release flag)
  • Check available disk space for output files
  • Monitor system resources (CPU, RAM, disk I/O)

Build Failures

# Nix
nix develop

WebAssembly Build
